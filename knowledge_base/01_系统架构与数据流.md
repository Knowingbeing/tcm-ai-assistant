# 系统架构与数据流

## 1. 分层架构

系统采用三层架构，各层职责清晰、单向依赖：

```
┌─────────────────────────────────────────────────────┐
│                    UI 层 (app.py)                     │
│  Streamlit 页面渲染 + 会话状态管理 + 用户交互处理     │
│  • 问诊 Tab：十问歌表单 → AI 辨证 → 结果展示          │
│  • 数据分析 Tab：记录统计 + 可视化图表                │
│  • 知识库 Tab：方剂/证型/中药 浏览                     │
│  • 系统设置 Tab：API Key + Supabase 诊断              │
├─────────────────────────────────────────────────────┤
│                  业务逻辑层                           │
│  ┌─────────────────┐  ┌──────────────────────────┐  │
│  │  llm_engine.py  │  │   supabase_client.py     │  │
│  │  • LLM 调用     │  │   • Supabase CRUD        │  │
│  │  • 规则兜底     │  │   • JSON 降级             │  │
│  │  • 多轮追问     │  │   • 错误翻译              │  │
│  │  • 知识注入     │  │   • 全链路诊断             │  │
│  └────────┬────────┘  └───────────┬──────────────┘  │
├───────────┼───────────────────────┼─────────────────┤
│           ▼   数据层               ▼                  │
│  ┌──────────────┐  ┌──────────────────────────────┐ │
│  │  tcm_data.py │  │  Supabase (PostgreSQL)       │ │
│  │  ten_asks.py │  │  • consultations 表          │ │
│  │  (内存常量)   │  │  • settings 表              │ │
│  │              │  │  • patients 表               │ │
│  └──────────────┘  │  JSON 文件 (本地兜底)         │ │
│                    └──────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

## 2. 核心数据流

### 2.1 问诊主流程（单轮）

```
用户输入
  │
  ├─ 主诉 (chief_complaint): 自由文本
  ├─ 症状 (symptoms): 标签选择 + 自定义输入
  ├─ 十问歌 (ten_asks_data): 10 维度结构化表单
  ├─ 舌象 (tongue_sign): 文本描述
  └─ 脉象 (pulse_sign): 文本描述
        │
        ▼
  _collect_symptoms_from_ten_asks(sess)
  合并十问歌数据 + sess["symptoms"] → 去重 → 症状列表
        │
        ▼
  TCMDiagnosisEngine.analyze_symptoms(
      chief_complaint, symptoms, tongue_sign, pulse_sign
  )
        │
        ├─ has_api_key == True ──► 构造 system prompt（含知识库）
        │                          ├─ 调用 LLM API (OpenAI SDK)
        │                          ├─ 解析 JSON 响应
        │                          └─ 成功 → 返回辨证结果 dict
        │                          └─ 失败 → 降级到规则引擎
        │
        └─ has_api_key == False ──► _rule_based_diagnosis()
                                    ├─ 关键词匹配 20+ 证型
                                    └─ 返回辨证结果 dict
        │
        ▼
  辨证结果 dict:
  {
    "syndrome": "太阳伤寒证",
    "syndrome_category": "六经辨证",
    "analysis": "分析文本...",
    "formula": "麻黄汤",
    "formula_adjustment": "加减建议...",
    "treatment_principle": "发汗解表、宣肺平喘",
    "confidence": 85
  }
        │
        ▼
  save_record(record) → _sb_save_record()
  ├─ Supabase 已配置 → insert into consultations
  └─ Supabase 未配置 → 追加到 JSON 文件
        │
        ▼
  load_records.clear()  # 失效缓存
        │
        ▼
  UI 展示辨证结果卡片
```

### 2.2 多轮问诊流程（P1 新增）

```
第 0 轮：
  用户提交初始症状
    │
    ▼
  engine.should_ask_followup(chief, symptoms, tongue, pulse, round=0)
    │
    ├─ 信息充分（舌/脉/寒热/汗/二便 全覆盖）──► need_followup = False
    │                                          直接 analyze_symptoms()
    │
    └─ 信息不足 ──► need_followup = True
                    questions = [{field, label, options}, ...]  (最多 2 个)
                    存入 sess["pending_questions"]
                    UI 渲染追问选项卡片

第 1 轮：
  用户回答追问
    │
    ▼
  _apply_followup_answer(sess, question, answer, engine)
  ├─ 将 answer 写入 sess[question["field"]]  (如 tongue_sign)
  ├─ 清空 sess["pending_questions"]
  └─ sess["round"] += 1
    │
    ▼
  再次调用 should_ask_followup(round=1)
    ├─ 仍需追问 ──► 继续追问（最多到 round=2）
    └─ 信息充分 ──► diagnose_with_conversation(session)
                     ├─ 拼接所有轮次的 messages
                     ├─ 调用 LLM 进行最终辨证
                     └─ 返回辨证结果

最终保存：
  save_record() 时 source = "chat"
  messages 字段存储完整对话历史 (JSONB)
  session_id 标识同一问诊会话
  round_index 标识轮次
```

## 3. 会话状态管理 (st.session_state)

Streamlit 的 session_state 是核心状态容器，以下为所有使用的 key：

| Key | 类型 | 说明 | 初始化位置 |
|-----|------|------|-----------|
| `symptoms` | `list[str]` | 当前选中的症状标签列表 | 问诊 Tab 初始化 |
| `ten_asks_data` | `dict` | 十问歌表单数据，key 为维度 key | 问诊 Tab 初始化 |
| `tongue_sign` | `str` | 舌象文本 | 问诊 Tab |
| `pulse_sign` | `str` | 脉象文本 | 问诊 Tab |
| `result` | `dict\|None` | 当前辨证结果 | analyze_symptoms 后 |
| `_api_key_ok` | `bool` | API Key 是否已验证 | 设置 Tab |
| `engine` | `TCMDiagnosisEngine\|None` | AI 引擎实例 | 设置 Tab |
| `session_id` | `str` | 多轮问诊会话 ID | 问诊 Tab |
| `round` | `int` | 当前问诊轮次 | 问诊 Tab |
| `messages` | `list[dict]` | 对话历史（OpenAI 格式） | 问诊 Tab |
| `pending_questions` | `list[dict]` | 待回答的追问问题 | should_ask_followup 后 |

### 关键修复记录

- **症状丢失 Bug（已修复）**：早期代码使用 `sess.get("ten_asks", {})` 读取十问歌数据，但实际存储 key 为 `"ten_asks_data"`，导致十问歌采集的症状丢失。已修正为 `sess.get("ten_asks_data", {})`。
- **has_api_key 判定 Bug（已修复）**：第一路判定 `st.session_state["_api_key_ok"]` 未使用 `.get()`，在 key 不存在时直接抛 KeyError。已修正为 `bool(st.session_state.get("_api_key_ok", False))`。

## 5. 四路 API Key 判定机制

为解决 API Key 在不同生命周期阶段的状态同步问题，系统采用四路级联判定：

```
def has_api_key(engine):
    # ① session_state 标志位（设置 Tab 验证后设置）
    if st.session_state.get("_api_key_ok", False):
        return True
    # ② engine 对象的 has_api_key 属性
    if engine and getattr(engine, "has_api_key", False):
        return True
    # ③ 磁盘 settings（Supabase settings 表 或本地文件）
    settings = load_settings_from_storage()
    if settings.get("api_key"):
        return True
    # ④ widget 当前值（用户刚输入但尚未保存）
    if st.session_state.get("api_key_input", "").strip():
        return True
    return False
```

**设计原因**：Streamlit 每次交互都会重新执行整个脚本，engine 对象可能被重建，session_state 可能被重置。四路判定确保在任意阶段都能正确检测到已配置的 API Key。
